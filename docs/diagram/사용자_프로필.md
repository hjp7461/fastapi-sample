# 사용자 프로필

본인 정보 조회/수정과 다른 사용자 정보 조회. 세 엔드포인트 모두 **인증 필요** (관리자 권한은 불요).

## 1. 내 정보 조회 — `GET /api/v1/users/me`

| 항목       | 값                                                      |
| ---------- | ------------------------------------------------------- |
| 핸들러     | `app/user/router.py:37 get_current_user_info`           |
| 의존성     | `get_current_user`                                      |
| 성공       | `200 OK` + `UserResponse`                               |
| 실패       | `401` (인증 실패) · `400` (비활성 사용자)              |

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>GET /users/me
    participant Dep as get_current_user

    Client->>Router: GET /api/v1/users/me<br/>Authorization: Bearer <token>
    Router->>Dep: Depends(get_current_user)
    Note over Dep: 인증 및 권한 다이어그램 참조<br/>JWT 디코드 + 사용자 조회 + 활성 검사

    alt 인증 실패
        Dep--xRouter: HTTPException(401/400)
        Router-->>Client: 401 / 400
    else 정상
        Dep-->>Router: User
        Note over Router: 본문은 current_user 그대로 반환
        Router-->>Client: 200 OK<br/>UserResponse
    end
```

### 핵심 포인트

- 라우터 본문은 추가 DB 조회 없이 의존성에서 받은 `User` 를 그대로 반환한다.
- 직렬화는 `response_model=UserResponse` 에 의해 자동 처리 → `hashed_password` 노출 방지.

## 2. 내 정보 수정 — `PUT /api/v1/users/me`

| 항목       | 값                                                              |
| ---------- | --------------------------------------------------------------- |
| 핸들러     | `app/user/router.py:45 update_current_user`                     |
| 의존성     | `get_current_user`                                              |
| 요청 본문  | `UserUpdate` (부분 업데이트, `exclude_unset=True` 적용)         |
| 성공       | `200 OK` + 갱신된 `UserResponse`                                |
| 실패       | `401` · `400` · `404` (이론상 발생 안 함, 인증 직후 본인 ID)   |

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>PUT /users/me
    participant Dep as get_current_user
    participant Service as UserService
    participant Repo as UserRepository
    participant Sec as security<br/>get_password_hash
    participant DB as SQLite

    Client->>Router: PUT /api/v1/users/me<br/>{username?, first_name?, password?, ...}
    Router->>Dep: Depends(get_current_user)
    Dep-->>Router: User (current_user)
    Router->>Service: update_user(current_user.id, user_in.dict(exclude_unset=True))

    opt password 포함 시
        Service->>Sec: get_password_hash(password)
        Sec-->>Service: hashed_password
        Note over Service: user_data["hashed_password"] = ...<br/>user_data.pop("password")
    end

    Service->>Repo: update(user_id, user_data)
    Repo->>DB: SELECT * FROM users WHERE id = ?
    DB-->>Repo: row

    alt 사용자 없음 (이론상 미발생)
        Repo-->>Service: None
        Service-->>Router: NotFoundException
        Router-->>Client: 404 Not Found
    else 정상
        Note over Repo: update_data = {k:v for k,v in ... if v is not None}
        Repo->>DB: UPDATE users SET ... WHERE id = ?
        Repo->>DB: COMMIT
        Repo->>DB: SELECT (재조회)
        DB-->>Repo: 갱신된 row
        Repo-->>Service: User
        Service-->>Router: User
        Router-->>Client: 200 OK<br/>UserResponse
    end
```

### 핵심 포인트

- **부분 업데이트**: 라우터에서 `user_in.dict(exclude_unset=True)` 로 호출자가 보낸 필드만 전달. 추가로 repository 의 `update` 가 `v is not None` 인 값만 갱신하므로 명시적 `null` 도 무시된다.
- **password 변경**: 서비스 계층에서 `password` → `hashed_password` 로 키 변환. 라우터/리포지토리는 평문을 모른다.
- repository `update` 는 UPDATE 후 SELECT 로 재조회한 결과를 반환 → 트리거나 DB 기본값을 반영.

## 3. 특정 사용자 조회 — `GET /api/v1/users/{user_id}`

| 항목       | 값                                                                                |
| ---------- | --------------------------------------------------------------------------------- |
| 핸들러     | `app/user/router.py:82 get_user_by_id`                                            |
| 의존성     | `require_self_or_admin` (path parameter `user_id` 자동 주입 + 권한 검증)              |
| 권한 정책  | **본인 또는 관리자만**                                                            |
| 성공       | `200 OK` + `Union[UserResponse, UserAdminView]` (viewer 별 분기, PR #15)         |
| 실패       | `401` (인증 실패) · `400` (비활성 사용자) · `403` (권한 부족) · `404` (사용자 없음) |

- 본인 조회 (`current_user.id == user.id`) → `UserResponse` (전체 PII)
- ADMIN 이 타인 조회 → `UserAdminView` (email 마스킹 + 이름 제외)

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>GET /users/{user_id}
    participant SelfAdmin as require_self_or_admin
    participant CurUser as get_current_user
    participant Service as UserService
    participant Repo as UserRepository
    participant DB as SQLite

    Client->>Router: GET /api/v1/users/{user_id}<br/>Authorization: Bearer <token>
    Router->>SelfAdmin: Depends(require_self_or_admin)
    SelfAdmin->>CurUser: Depends(get_current_user)
    Note over CurUser: 인증_및_권한.md 참조

    alt 인증 실패
        CurUser--xSelfAdmin: HTTPException(401/400)
        SelfAdmin-->>Router: 전파
        Router-->>Client: 401 / 400
    else 인증 성공
        CurUser-->>SelfAdmin: current_user
        alt current_user.id != user_id AND not current_user.is_admin()
            Note over SelfAdmin: 권한 검사를 존재 확인보다 먼저<br/>(ID 열거 공격 차단)
            SelfAdmin-->>Router: HTTPException(403)
            Router-->>Client: 403 Forbidden<br/>"Not enough permissions"
        else 권한 OK (본인 또는 관리자)
            SelfAdmin-->>Router: current_user
            Router->>Service: get_user(user_id)
            Service->>Repo: get_by_id(user_id)
            Repo->>DB: SELECT * FROM users WHERE id = ?
            DB-->>Repo: row | None
            alt 사용자 없음
                Repo-->>Service: None
                Service-->>Router: NotFoundException
                Router-->>Client: 404 Not Found
            else 사용자 존재
                Repo-->>Service: User
                Service-->>Router: User
                alt current_user.id == user.id (본인)
                    Router-->>Client: 200 OK<br/>UserResponse (전체 PII)
                else ADMIN 이 타인 조회
                    Note over Router: build_admin_view(user)<br/>email 마스킹 (settings.USER_ADMIN_EMAIL_MASKING)<br/>+ first_name/last_name 제외
                    Router-->>Client: 200 OK<br/>UserAdminView
                end
            end
        end
    end
```

### 핵심 포인트

- **권한 검사를 의존성으로 추출** — 라우터 본문은 비즈니스 로직 (service 호출 + 404 매핑) 만 담당. 권한 분기는 `require_self_or_admin` 의존성이 책임진다.
- **권한 평가가 존재 확인보다 먼저** 다. 일반 사용자가 ID 를 바꿔가며 `403` vs `404` 응답 차이로 사용자 ID 의 존재 여부를 열거하는 공격을 차단한다.
  - 일반 사용자가 **존재하는 타인 ID** 조회 → `403`
  - 일반 사용자가 **존재하지 않는 ID** 조회 → `403` (동일)
  - 관리자만 `404` 를 받을 수 있음
- FastAPI 가 `require_self_or_admin(user_id: int, ...)` 의 `user_id` 를 라우터의 path parameter 와 동일 이름으로 자동 주입.
- 권한 비교는 도메인 메서드 (`User.is_admin()`) 로 표현됨. 권한 계층 (STAFF ⊂ ADMIN) 은 `User.is_staff_or_above()` 로 분리되어 있다.
- **응답 PII 다중방어** (PR #15): ADMIN 이 타인을 조회하면 `UserAdminView` 로 전환되어 email 마스킹 + 이름 제외. email 마스킹은 `USER_ADMIN_EMAIL_MASKING` 환경 변수로 토글 가능 (기본 True, dev 디버깅 시 False 명시, 자세한 운영 매트릭스는 [`RUNBOOK §2`](../RUNBOOK.md) 참조).
