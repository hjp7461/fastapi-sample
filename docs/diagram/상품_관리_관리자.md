# 상품 관리 (관리자 전용)

상품의 생성/수정/삭제와 재고 변경. **모두 `get_current_active_admin` 의존성으로 보호된다.**

> 모든 다이어그램의 **인증/권한 단계는 동일** 하므로 첫 다이어그램(상품 생성)에 한 번 펼쳐 그리고, 이후에는 "관리자 검사 통과 후" 로 축약한다. 인증 단계의 상세 흐름은 [`인증_및_권한.md`](./인증_및_권한.md) 참조.

---

## 1. 상품 생성 — `POST /api/v1/products/`

| 항목     | 값                                                  |
| -------- | --------------------------------------------------- |
| 핸들러   | `app/product/router.py:22 create_product`           |
| 의존성   | `get_current_active_admin`                          |
| 요청 본문 | `ProductCreate { name, price, category, ... }`     |
| 성공     | `201 Created` + `ProductResponse`                   |
| 실패     | `401` · `403` · `400` (ValidationException)         |

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>POST /products/
    participant Admin as get_current_active_admin
    participant User as get_current_user
    participant Service as ProductService
    participant Repo as ProductRepository
    participant DB as SQLite

    Client->>Router: POST /api/v1/products/<br/>Authorization: Bearer <token><br/>{name, price, category, ...}
    Router->>Admin: Depends(get_current_active_admin)
    Admin->>User: Depends(get_current_user)
    Note over User: JWT 디코드 + 사용자 조회

    alt 인증/권한 실패
        User--xAdmin: HTTPException
        Admin-->>Router: 전파
        Router-->>Client: 401 / 400 / 403
    else 관리자 통과
        Admin-->>Router: User
        Router->>Service: create_product(product_data)
        Service->>Repo: create(Product(...))
        Repo->>DB: INSERT INTO products (...)
        Repo->>DB: COMMIT
        Repo->>DB: SELECT (refresh)
        DB-->>Repo: row with id
        Repo-->>Service: Product
        Service-->>Router: Product
        Router-->>Client: 201 Created<br/>ProductResponse
    end
```

### 핵심 포인트

- 입력값에 `category` 가 없으면 도메인 기본값 `ProductCategory.OTHER` 가 적용된다.
- `inventory` 미지정 시 `0`, `is_active` 미지정 시 `True`.
- 라우터에 `ValidationException` 핸들러가 선언되어 있지만 현재 `ProductService.create_product` 는 이 예외를 던지지 않는다 — 향후 비즈니스 규칙 추가를 위한 사전 배치.

## 2. 상품 수정 — `PUT /api/v1/products/{product_id}`

| 항목       | 값                                                              |
| ---------- | --------------------------------------------------------------- |
| 핸들러     | `app/product/router.py:54 update_product`                       |
| 의존성     | `get_current_active_admin`                                      |
| 요청 본문  | `ProductUpdate` (부분 업데이트)                                 |
| 성공       | `200 OK` + 갱신된 `ProductResponse`                             |
| 실패       | `401` · `403` · `404`                                           |

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>PUT /products/{id}
    participant Admin as get_current_active_admin
    participant Service as ProductService
    participant Repo as ProductRepository
    participant DB as SQLite

    Client->>Router: PUT /api/v1/products/{id}<br/>Authorization: Bearer <token><br/>{name?, price?, ...}
    Router->>Admin: Depends(get_current_active_admin)
    Note over Admin: 관리자 검사 통과 가정

    Admin-->>Router: User
    Router->>Service: update_product(id, product_in.dict(exclude_unset=True))
    Service->>Repo: update(id, data)
    Repo->>DB: SELECT * FROM products WHERE id = ?
    DB-->>Repo: row | None

    alt 상품 없음
        Repo-->>Service: None
        Service-->>Router: NotFoundException
        Router-->>Client: 404 Not Found
    else 상품 존재
        Note over Repo: update_data = {k:v for ... if v is not None}
        Repo->>DB: UPDATE products SET ... WHERE id = ?
        Repo->>DB: COMMIT
        Repo->>DB: SELECT (재조회)
        DB-->>Repo: 갱신된 row
        Repo-->>Service: Product
        Service-->>Router: Product
        Router-->>Client: 200 OK<br/>ProductResponse
    end
```

### 핵심 포인트

- 사용자 프로필 수정과 동일한 패턴 — `exclude_unset=True` + repository 내부 `v is not None` 필터.
- `inventory` 도 본 엔드포인트로 변경 가능하지만, **원자적 증감** 이 필요하면 아래의 `PATCH /inventory` 를 사용해야 한다.

## 3. 상품 삭제 — `DELETE /api/v1/products/{product_id}`

| 항목       | 값                                                              |
| ---------- | --------------------------------------------------------------- |
| 핸들러     | `app/product/router.py:74 delete_product`                       |
| 의존성     | `get_current_active_admin`                                      |
| 성공       | `204 No Content`                                                |
| 실패       | `401` · `403` · `404`                                           |

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>DELETE /products/{id}
    participant Admin as get_current_active_admin
    participant Service as ProductService
    participant Repo as ProductRepository
    participant DB as SQLite

    Client->>Router: DELETE /api/v1/products/{id}<br/>Authorization: Bearer <token>
    Router->>Admin: Depends(get_current_active_admin)
    Note over Admin: 관리자 검사 통과 가정

    Admin-->>Router: User
    Router->>Service: delete_product(id)
    Service->>Repo: get_by_id(id)
    Repo->>DB: SELECT * FROM products WHERE id = ?
    DB-->>Repo: row | None

    alt 상품 없음
        Repo-->>Service: None
        Service-->>Router: NotFoundException
        Router-->>Client: 404 Not Found
    else 상품 존재
        Repo-->>Service: Product
        Service->>Repo: delete(id)
        Repo->>DB: DELETE FROM products WHERE id = ?
        Repo->>DB: COMMIT
        DB-->>Repo: rowcount
        Repo-->>Service: True
        Service-->>Router: True
        Router-->>Client: 204 No Content
    end
```

### 핵심 포인트

- **하드 삭제** 다. 소프트 삭제(`is_active=False`)가 필요하면 `PUT /products/{id}` 로 대체 가능.
- 서비스 계층에서 SELECT → DELETE 의 2-step 으로 존재 검증을 한 뒤 삭제 — DELETE 자체로도 `rowcount` 로 판별 가능하지만 명시적 404 를 위해 분리.

## 4. 상품 재고 변경 — `PATCH /api/v1/products/{product_id}/inventory`

| 항목       | 값                                                                        |
| ---------- | ------------------------------------------------------------------------- |
| 핸들러     | `app/product/router.py:107 update_product_inventory`                      |
| 의존성     | `get_current_active_admin`                                                |
| 요청 본문  | `ProductInventoryUpdate { quantity_change: int }` (양수=증가, 음수=감소) |
| 성공       | `200 OK` + 갱신된 `ProductResponse`                                       |
| 실패       | `401` · `403` · `404` · `400` (재고 부족)                                |

```mermaid
sequenceDiagram
    autonumber
    actor Client
    participant Router as Router<br/>PATCH /products/{id}/inventory
    participant Admin as get_current_active_admin
    participant Service as ProductService
    participant Repo as ProductRepository
    participant DB as SQLite

    Client->>Router: PATCH /api/v1/products/{id}/inventory<br/>Authorization: Bearer <token><br/>{quantity_change: ±N}
    Router->>Admin: Depends(get_current_active_admin)
    Note over Admin: 관리자 검사 통과 가정

    Admin-->>Router: User
    Router->>Service: update_inventory(id, quantity_change)
    Service->>Repo: get_by_id(id)
    Repo->>DB: SELECT * FROM products WHERE id = ?
    DB-->>Repo: row | None

    alt 상품 없음
        Repo-->>Service: None
        Service-->>Router: NotFoundException
        Router-->>Client: 404 Not Found
    else 상품 존재
        Repo-->>Service: Product(inventory=N)
        alt quantity_change < 0 AND abs(quantity_change) > inventory
            Service-->>Router: BusinessLogicException
            Router-->>Client: 400 Bad Request<br/>"Not enough inventory"
        else 충분한 재고
            Service->>Repo: update_inventory(id, quantity_change)
            Note over Repo: new_inventory = current + quantity_change<br/>(음수 보호: max(0, new))
            Repo->>DB: UPDATE products SET inventory = ? WHERE id = ?
            Repo->>DB: COMMIT
            Repo->>DB: SELECT (재조회)
            DB-->>Repo: 갱신된 row
            Repo-->>Service: Product
            Service-->>Router: Product
            Router-->>Client: 200 OK<br/>ProductResponse
        end
    end
```

### 핵심 포인트

- **원자성 주의**: 현재 구현은 SELECT → 검증 → UPDATE 의 3-step. 동시에 두 요청이 들어오면 race condition 으로 음수 재고가 발생할 수 있다. 단일 SQL (`UPDATE ... SET inventory = inventory + ?`) 또는 트랜잭션 격리 수준 격상이 필요한 경우 보강 필요.
- repository 의 **이중 안전망**: `new_inventory < 0` 인 경우 0 으로 클램프 (서비스 단 검증을 통과한 후 race 등으로 음수가 되는 케이스 보호).
- `quantity_change` 가 0 이어도 UPDATE 가 실행된다 (불필요한 쓰기). 최적화 여지.
- 두 가지 예외가 다른 HTTP 코드로 매핑:
  - `NotFoundException` → 404
  - `BusinessLogicException` → 400
